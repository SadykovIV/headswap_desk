# Независимый аудит активации, настроек и медиа — 0.6.0

Дата: 2026-11-09. Проверены пункты 1, 3, 9, 10, 11, 12, 16 пользовательского плана. База сравнения — оригинальный HeadSwap `8ab72c8846e7777ac355ae6260ab1ce78cba0af4`; более поздняя сверенная ревизия изменяет музыкальные слоты лаунчера, а не перечисленные ниже пути. Поддерживаемый диапазон этого APK — Android 13–17 (`minSdk=33`), а не Android 10–12.

## Найденные дефекты

1. **P2 — ответ предыдущей попытки мог примениться к новой.** `PhonePairingService.serviceAction` использовал одинаковые component/action/requestCode и `FLAG_UPDATE_CURRENT`. Nonce находился только в extras, которые не участвуют в идентичности PendingIntent. Сценарий: сохранить действие A → отменить A → начать B → отправить сохранённое действие A. Android обновлял его extras до token B. Исправление: nonce и действие включены в `Intent.data`; extras остаются дополнительной проверкой. В `PhonePairingUiProbe` добавлен сценарий A→B с реальными Android PendingIntent для ответа и отмены.
2. **P2 — старая отмена могла оставить пустую foreground-службу.** `onStartCommand` вызывал `startForeground` до проверки действия. Старый CANCEL после завершения попытки не попадал ни в отмену worker, ни в `stopSelf`. Исправление: foreground начинается только для START; старые ответы и отмены без worker завершают службу. Первый целевой прогон API34 дополнительно обнаружил `ForegroundServiceDidNotStartInTimeException`: PendingIntent для старого ответа требовал нового foreground даже при немедленном отказе. Поэтому REPLY/CANCEL используют обычный service PendingIntent; START сохраняет foreground и подтверждает обязательство Android даже при изменившихся между вызовом и запуском настройках. Добавлена проверка отсутствия уведомлений и worker после старого CANCEL.
3. **P2 — отключённый канал делал ввод кода невидимым.** `DexSetupActivity.startNotificationActivation` проверял только разрешение и общий `areNotificationsEnabled`, но не отключение отдельного канала. Сценарий: выключить «Ввод кода сопряжения», оставить остальные уведомления разрешёнными, запустить первое сопряжение. Служба ожидала код пять минут без поля ввода. Исправление: проверка APP / progress channel / code channel в UI и service; ссылка на точный канал и самостоятельный вариант ручного ввода. Повторная активация с сохранённым ключом не требует канала кода. Проверка выполняется повторно после разрешения уведомлений/локальной сети. Добавлены unit-проверки и инструментальная проверка реальных настроек каналов.
4. **P2 — Wi-Fi обходил подготовку выбранного backend.** Дополнительно найдено другим аудитором и подтверждено: `DexSetupActivity.beginConnect` при Wi-Fi возвращался до запроса Shizuku, а legacy ADB никогда не проходил общую проверку. Вне главного экрана legacy, наоборот, разрешался без предварительной проверки. Исправление: единая подготовка доступа, затем выбор USB/Wi-Fi; legacy Ready продолжает в выбранный транспорт. Для него хранится только неперсистентное свидетельство успешного ADB-probe текущего endpoint/сопряжения. Новый probe, новое сопряжение и ошибка сбрасывают его; generation token не даёт позднему старому результату восстановить готовность. Сам `DexConnector` повторно аутентифицируется. Это не бессрочное разрешение и не обход ADB. Добавлены проверки смены endpoint, сброса и поздних результатов; Shizuku permission dialog физически ещё не перепроверен.
5. **P2 — поздний callback старого экземпляра службы мог очистить новую попытку.** `activate.finally` отправлял `finish` без проверки уничтоженного экземпляра; READY вызывал завершение ещё и из worker. Теперь обновления уведомлений и завершение сериализованы на main с проверкой экземпляра/попытки, завершение одноразовое. Отмена и момент окончательной отправки активации упорядочены общим lock. Runtime-регрессия повторяет старый terminal callback после запуска B и проверяет сохранность её уведомления и active-state.

Эти исправления во время аудита внесены по поручению ведущего агента. Статус каждого нового прогона приведён ниже; проверки на эмуляторе не заменяют физическую магнитолу. Общие прежние отчёты не изменялись.

## Целевые прогоны аудита

- Общая build24 успешно собрана. Новые `PairingNotificationPolicyTest` (4) и `LegacyAdbReadinessTest` (3) прошли без ошибок и пропусков.
- API34 build24: `wireless-opt-out` прошёл на настоящей BridgeService с TCP6 listener и принятым каналом; после отключения опции служба/канал закрылись и не перезапустились. `media-artwork` прошёл новую цепочку MediaSession → CarLifeSession → декодирование MEDIA_INFO на моделируемом ГУ, для USB и TCP6, включая удаление обложки.
- API34 build24: `pairing-ui` выявил описанное выше падение при старом REPLY. Сохранены `api34-pairing-ui-build24.txt` и отдельный crash log. Повторный `pairing-ui` build26 прошёл полностью: APP-denied, оба отключённых канала, A→B, старый callback экземпляра, старые reply/cancel после завершения. Новый START в промежутке между finish и onDestroy всегда подтверждает foreground и немедленно завершает этот terminal-экземпляр; точный порядок системной очереди отдельно не форсируется тестом и не выдаётся за измеренный сценарий.
- API34 build24: `surface-timing` остановился до кодека из-за недопустимого размера тестового кадра 320×180. Это ошибка QA-фикстуры; размер исправляет другой агент. Исходный результат сохранён как `api34-surface-timing-build24.txt`.
- API33 с чистыми данными, main26/QA27: полностью прошли `pairing-ui`, `surface-timing`, `hardware-input`, `desktop-knob`, `media-artwork`, `wireless-opt-out`. С QA28 также прошёл `wireless-dashboard`: настоящий внешний UID и Binder открыли дочерние «Настройки» и подтверждение управления панелью при wireless=true. Итого семь целевых сценариев PASS. Перед установкой и после последнего завершённого теста эмулятор падал в host gRPC; отдельная обезличенная диагностика сохранена. Это не падение Android-приложения.
- API34: `pairing-ui`, `surface-timing`, `hardware-input`, `desktop-knob` прошли на main26/QA26. `media-artwork` и `wireless-opt-out` прошли на build24, после чего их production-пути не менялись. Историческая неудача provider-фикстуры не помечена успехом; её отдельный повтор QA28 выполняет владелец теста.
- API37 main26/QA27: полный `pairing-ui` прошёл после адаптации только QA к TestApi `NotificationManager.updateNotificationChannel`. Точная сигнатура старого Binder-метода не изменилась, но API37 скрывает её как `MAX-TARGET-O`; это подтверждено разбором framework.jar данного AVD. Production использует публичные чтения notification/channel state и не зависит от этого скрытого setter.
- API33/34/35 provider regression выявил недоступный `Files.writeString` только в test APK (`DesktopPanelFixture`); QA28 использует совместимый FileOutputStream. Успех API33 после исправления прочитан из окончательного `api33-wireless-dashboard.txt`; исходная неудача сохранена отдельно.
- В прочитанных финальных `pairing-ui` API33/34/37 нет веток `NOT_RUN` или `SKIP`: APP-denied и оба канала проверены фактически. Условный NOT_RUN для отсутствующего Android TestApi остаётся корректным поведением теста, но на этих трёх AVD не потребовался.
- Новые результаты аудита отделены от старой матрицы: `artifacts/runtime-qa/0.6.0-audit/`. SHA main26 и QA26/27/28 сохранены в JSON manifests рядом с результатами. Main APK не менялся при исправлениях QA27/28.

## Источники и актуальность тестов

- Дополнительная проверка реального ввода API33 на main32 завершилась timeout при ожидании маркера обычной кнопки «Назад» без открытой клавиатуры. Исходный FAIL сохранён в `api33-desktop-knob-build32.txt`. **Этот результат сам по себе не доказывает потерю Back:** маркер тестовой Activity записывался только в legacy `onKeyUp`, тогда как Android может обработать predictive Back без этого callback. Последующий API37 обнаружил именно такой недостаток QA. Живой logcat предыдущего API33 прогона не сохранён, поэтому причинность старого timeout остаётся непроверенной до отдельного raw-parent diagnostic с корректной test Activity. Прежний `hardware-input` также не покрывал этот сценарий, поскольку использовал другое окно родителя. В main33 владелец ввода сохранил общий выбор IME/Home и двойного Back в службе, а действие собственного родителя направил через callback точного живого владельца. Это сохраняет обычный `pane.back()` и его очистку окон, не требует фокусируемого Android-окна родителя и отклоняет устаревший callback после Home/смены приложения.
- На той же main32 полностью прошли `wireless-dashboard` (реальное закрытие собственного диалога одним Back, DPAD/OK/rotary и восстановление фокуса дочернего окна) и `hardware-input` (включая общую последовательность двойного Back после диалога). Доказательства сохранены с суффиксом `-build32.txt`. API33 не обязан сообщать глобальный `hasWindowFocus=true` для видимого диалога на отдельном дисплее; проверка теперь использует реально нарисованное окно, его флаги и наблюдаемое закрытие.
- **Текущий целевой результат API33 main33: все три сценария PASS.** `desktop-knob` подтверждает реальный `singleBackReachesDisplayedChildWithoutIme`, отказ старого callback после Home и возврат фокуса каталогу. `wireless-dashboard` подтверждает реальное закрытие диалога, восстановление фокуса дочернего окна и отказ callback старого диалога после его замены. `hardware-input` подтверждает общую последовательность modal Back→double Back Home, фокус двух дочерних окон и rotary/OK. Все boolean assertions равны true, кроме информационного `modalHasGlobalWindowFocus=false`; пропусков нет. Файлы: `api33-{desktop-knob,wireless-dashboard,hardware-input}-build33.txt`; диагностика реального InputDispatcher сохранена отдельно в `api33-modal-input-build33.txt`. Установленные SHA проверены перед запуском: main `e6e5b32dff72354005486f74e995a472502c4d559e14da44e6a627fdb704e021`, QA `ab3bad667f392712e65c3c4eb429b99b5dab2ee27ff8bf6a695c2d58635243b5`.
- **Контроль QA34 на неизменённом main33:** test Activity теперь регистрирует публичный `OnBackInvokedDispatcher`, поэтому её наблюдение учитывает predictive Back. Обычный `desktop-knob` повторно PASS. Отдельная диагностическая `desktop-knob-raw-back` обошла новый host callback и однократно отправила Back прежним raw-parent путём. На API33 за 2500 ms callback не наблюдался (`rawBackCallbackObserved=false`), дочерняя задача осталась живой (`rawBackChildTaskAlive=true`), marker пустой. Это воспроизведённая граница прежнего маршрута на данном AVD, а не доказательство причины старого32 timeout по одному отсутствующему legacy marker. Диагностическая проба завершилась штатно: её `INSTRUMENTATION_CODE=-1` означает успешное наблюдение, **не** успешную доставку raw Back. Результаты: `api33-desktop-knob-build34.txt`, `api33-desktop-knob-raw-back-build34.txt`; дополнительные post-cleanup dumpsys/logcat сохранены отдельно. QA SHA `1277e22c45664a42058d33466c8e85915f7cf8362971bf4230fe5467d8cc939f` проверена перед установкой. После проверки остановлен только тестовый AVD33.

- Реальные результаты находятся в `artifacts/runtime-qa/0.6.0-input-matrix/`; сохранённая матрица относится к функциональной build21. Build23 меняла бренд и прошла отдельный визуальный probe.
- API33 полное новое self-pairing осталось непроверенным из-за отключившегося отладочного транспорта эмулятора; успешный API37 не переносится на API33 автоматически.
- Причину channel-block подтверждает разделение package/channel разрешений в [AOSP NotificationManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/services/core/java/com/android/server/notification/NotificationManagerService.java). Обычное создание канала не отменяет блокировку пользователя.
- Для инструментальной APP-denied проверки применяется только тестовый Android API без убийства приложения. Если он отсутствует/запрещён на версии AVD, результат этой ветки должен быть `NOT_RUN`, а не ошибка продукта и не PASS. Остальные проверки продолжаются; чистая policy-проверка APP-denied остаётся обязательной.
