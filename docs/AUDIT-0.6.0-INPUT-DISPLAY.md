## 4. Что действительно гарантирует политика дисплея

`DesktopModePolicy`, `DesktopDisplayIsolation`, `DelegatedDesktopRuntime` и `DexUserService` запрашивают независимую группу и ALWAYS_UNLOCKED только при наличии соответствующего временного разрешения. Проверяется фактическая группа, а не только успешное создание Surface или наличие разрешения. Wake lock привязан к подтверждённой группе собственного дисплея. Снятия пароля телефона, разблокировки keyguard и глобального отключения блокировки здесь нет.

Ранее сохранённые инструментальные доказательства находятся в `artifacts/runtime-qa/0.6.0-input-matrix` соседнего рабочего каталога. `api33..36-display-isolation.txt` фиксируют настоящий PIN keyguard, внутреннюю панель OFF и проекцию ON. `api37-display-isolation.txt` фиксирует группу 0 и обе панели OFF. Успешное завершение самого probe не означает поддержку независимости: нужно читать `independent`, группу и состояния экранов.

Нельзя обобщать это на все прошивки Android17. Текущий публичный AOSP main в `LogicalDisplayMapper` и `VirtualDisplayAdapter` содержит обычную обработку OWN_DISPLAY_GROUP; оригинал отдельно документирует `separate_timeouts`, а доступный нам API37 фактически возвращает группу 0. Конкретная реализация этой ветки не подтверждена просмотренным публичным main. Приложение поэтому ориентируется на capability наблюдаемого дисплея, а не на номер Android.

Samsung DeX использует отдельный штатный путь Samsung и собственные флаги. Это осмысленный профиль производителя, но новая независимость его физической блокировки не проверена на настоящем Samsung в этом аудите. Также приложение, которое само прекращает работу при блокировке пользователя или запрещает защищённую проекцию, не обязано продолжать вывод только потому, что дисплей ALWAYS_UNLOCKED.

### Есть ли правильный VirtualDevice без поддельной CDM-привязки

В проверенном AOSP `VirtualDeviceManagerService.createVirtualDevice()` требует CREATE_VIRTUAL_DEVICE, принадлежность association вызывающему UID/package и, при `persistentDeviceIdApi`, профиль APP_STREAMING, AUTOMOTIVE_PROJECTION либо NEARBY_DEVICE_STREAMING. Обычный Bluetooth association с `profile=null` не проходит этот профильный фильтр. `AssociationRequestsProcessor` перед сохранением профильного association получает соответствующую роль. Streaming-роли имеют `systemOnly=true`; automotive — также `static=true`. Разрешения запроса streaming-profile имеют уровень signature|privileged. Одного временного CREATE_VIRTUAL_DEVICE или пользовательского подтверждения реального Bluetooth-устройства недостаточно для установленного пользователем APK.

Оригинальный `VdmHostMain` создаёт association для `com.android.shell` через синтетический restore payload и резервную shell-команду. Это не обычный пользовательский CDM-процесс, и он не перенесён.

Отдельно проверен менее категоричный вариант: системный пакет Shell действительно объявляет streaming-profile permissions. Настоящий, подтверждённый пользователем association от имени Shell **теоретически** может использоваться отдельным Shell-хостом. Это не association нашего APK, и наш основной процесс не может воспользоваться им под своим UID. Такая архитектура потребует отдельного исследования жизненного цикла привилегированного хоста при adbd/USB restart, реального CDM UX и аппаратного ГУ. Она не реализована и не выдаётся за найденное универсальное решение. OEM/system integration остаётся штатным способом предоставления роли; в текущей установке поддерживается гашение панели HeadSwap без keyguard.

Существующее модельное исключение `PhonePanelPolicy.needsPhoneCurtain(HONOR, ABR-LX1)` сохранено. Оно выбирает затемнение вместо аппаратного гашения на устройстве с ранее наблюдавшимся отключением проекции. Это именно частное исключение, а не универсальная capability-проверка. Удалять его без повторного теста этого телефона означало бы возможную регрессию; его наличие не скрыто.

## 5. Back и маршрутизация

Первый Back не откладывается для ожидания второго; сохраняется приоритет собственного child, в котором открыта IME. Второе завершённое нажатие за 500 мс возвращает выбранный рабочий стол. Повтор одного DOWN не считается вторым нажатием. DOWN/UP удерживают один живой токен дисплея; закрытие child не переносит UP в чужое окно.

Новый явный сброс последовательности нужен для локального semantic input и голосовой команды, которые не проходят `injectKey`. Это служебный метод с тем же `enforceClient` и сериализацией, а не фиктивный KEYCODE_UNKNOWN. `showDesktop` и прямой child touch также сбрасывают предыдущий Back. В резервном Samsung ADB-коннекторе последовательность уже сбрасывалась на любой другой key; сырые NAVI/MUSIC теперь тоже не инжектируются.

Повторный `HardwareInputProbe` на API37 (`api37-hardware-input-build24.txt`) выявил ошибку: первый RunningTask указывал parent после касания child. Прежний PASS с одним child не доказывал надёжность task ordering. `DesktopFocusReader`, его gateway API и runtime query удалены. Теперь адресат выбирается из токена последнего успешного собственного launch/touch; обе половины key gesture по-прежнему закреплены за одним токеном. Home переключает на parent, удаление child немедленно инвалидирует его выбор, новый Session не наследует старый выбор. Ассистент передаёт ID фактически запущенного собственного дисплея через проверяемый private API. Приоритет IME для Back сохранён отдельно.

Новый regression переключает два реальных child касаниями, затем проверяет поступившие key events в журнале каждого тестового окна, а не значение сомнительного getTasks. Это проверка producer/input routing; она не выдаётся за отдельную проверку геометрии композитора двух плиток. В build26 этот сценарий прошёл на API34, но API37 выявил отдельный ранний ввод: второй Task уже зарегистрирован, а touchable window ещё отсутствует. В сохранённом logcat `interceptKeyBeforeQueueing` занял 4950 мс из-за перехода WindowManager; deadline сервиса ввода — 2000 мс. Режим инжекта уже ASYNC. Новый QA ждёт настоящий кадр собственного тестового окна и focus callback, затем отправляет ровно один touch и проверяет его доставку перед key. Это не повтор до удачи и не увеличение таймаута production.

**Непройденный edge:** аппаратная клавиша сразу после запуска child, до готовности его окна, ещё способна попасть в медленную системную политику перехода. Исправление выбора собственного токена не объявляется исправлением этой гонки. Отдельное production-решение readiness до первого окна не реализовано; гарантии тестов относятся к готовым окнам.

## 6. Почему стандартный Intent не означает «Алиса как в оригинале»

`DesktopAssistant` проверяет реальные экспортируемые ASSIST/VOICE_COMMAND Activity и не переносит задачи с телефона. STANDARD entry может получить отдельную задачу; singleton допускается лишь при подтверждённой задаче на своём экране и полном доступе к списку задач. Это безопасное ограничение размещения, но не контракт Яндекса на открытие встроенной Алисы в текущем окне Навигатора.

Оригинальные `PhoneAssistant`, `LauncherActions` и ADR0034 используют отдельное приложение «Яндекс — с Алисой», его AssistantActivity/MainActivity, скрытый дочерний экран и наблюдение за задачами. ADR прямо описывает перемещение телефонного окна в течение первых секунд, закрытие лишних задач Навигатора и однажды оставшееся окно, перехватывавшее жесты. Эти завязки на внутреннюю реализацию Яндекса противоречат требованию универсального решения и не перенесены.

Официальная справка Навигатора описывает кнопку Алисы внутри приложения, разрешение микрофона и голосовую активацию; универсальный внешний Intent для этой кнопки в просмотренной документации не опубликован. Отсутствие такого контракта нельзя заменить угадыванием Activity/URI.

Микрофон CarLife в `AaBridge` направляется в `AaPeer.sendMicPcm`. Рабочие столы этот метод не реализуют; реализация есть у Android Auto `AapSession`. Следовательно, захват USAGE_ASSISTANT для воспроизведения ответов и запуск Activity не доказывают ввод голоса через микрофон автомобиля. Честный статус пункта6 — **PARTIAL**, без заявления о совместимости с Навигатором/микрофоном ГУ.

## 7. Исправленный контракт шайбы

`DesktopHardwareUi` регистрирует только живую собственную Activity конкретного вторичного дисплея. Коннектор повторно проверяет поколение и ID после переключения на главный поток. Каталог перехватывает вращение/наклоны/OK только когда показан сам каталог; чужое приложение сохраняет DPAD fallback. Собственные элементы определяются моделью Activity, без Accessibility, UIAutomator или чтения окон стороннего приложения.

`DesktopKnobFocus` оперирует стабильными ID приложений и контролов, включая ещё не видимые строки. Вращение переходит по одному элементу, наклон — по геометрии. Выбор прокручивает список, а рамка отрисовывается внутри карточки. Первое движение или OK после touch лишь показывает рамку; скрытая цель не активируется. Каталог, закреплённые приложения, Back, Home и кнопка выбранного компонента участвуют в обходе.

NAVI/MUSIC собственного Android Desktop используют только стандартные MAIN+APP_MAPS/APP_MUSIC category handlers. Если есть несколько кандидатов без default — пользователь выбирает; если ни одного — каталог объясняет отсутствие поддерживаемого обработчика. Пакеты не угадываются. DriveDeck/DeX не получают фиктивный NAVI=65538 или Android MUSIC, который система могла бы обработать на телефоне: эти launcher actions там не заявлены. Повороты/направления/OK для чужого окна требуют поддержки DPAD самим приложением.

Добавлены `DesktopKnobFocusTest`, `DesktopKnobProbe` (реальный каталог, offscreen scroll, пиксели рамки, touch/reveal, OK→child, Home) и новые проверки `HardwareInputProbe`. Новый `wireless-dashboard` использует внешний test-APK provider с настоящим Binder v1 и проверяет появление Settings в child и диалога подтверждения панели при wireless=true. Readiness транспортного сеанса задаётся стендом; физический Wi-Fi и питание этим probe не проверяются. Повтор на API37 с production build26 и QA build27 прошёл с первой попытки: `hardware-input` подтвердил оба child по очереди, Back и сброс последовательности; `desktop-knob` — 210 фактических пикселей рамки, offscreen scroll, touch/reveal, OK→child и Home; `wireless-dashboard` — настоящий внешний Binder, Settings в дочернем окне и диалог панели. Основной APK между неудачной QA26 и успешной QA27 не менялся. Файлы `api37-*-build27.txt` и неудачные `*-build24.txt` / `*-build26.txt` сохранены в `artifacts/runtime-qa/0.6.0-audit` рабочего каталога.

Причины отдельных ошибок стенда не замаскированы повторами: (1) TaskInfo появлялся до готового окна и приводил к раннему вводу — теперь ждём собственный кадр/focus и факт доставки единственного touch; (2) callback ImageReader читал буфер после закрытия reader — теперь сначала detach и drain; (3) provider broadcast не был синхронизирован с registerReceiver — теперь первый и единственный запрос следует после ready-маркера внешнего процесса; (4) на API35 подтверждён NoSuchMethodError для тестового Files.writeString — QA28 использует совместимый FileOutputStream/UTF-8. Последнее исправление затрагивает только тестовый APK и журнал готовности внешнего fixture. Проверки результата (реальный key, pixels, child task, диалог) сохранены. Основной build26 прошёл эту целевую матрицу на API33–37: по семь probes (hardware-input, desktop-knob, wireless-dashboard, pairing-ui, wireless-opt-out, media-artwork, surface-timing). API33/35/36 и повтор API34 provider используют QA28 с FileOutputStream; API37 — QA27. API34 hardware-input дополнительно повторён с QA28 и строгой готовностью окна. Все исходные сбои сохранены; main APK в этих повторах не менялся.

### Дополнительный найденный случай: собственный модальный диалог

После этой матрицы read-only review нашёл функциональный пропуск: `hardwareAvailable=false` во время трёх собственных AlertDialog отправлял DPAD/OK нижележащему child. Наличие child IME могло также увести Back от модального окна. Исправление не скрыто первоначальными PASS: оно потребовало нового build29 и отдельной проверки.

Теперь видимый диалог собственного живого parent получает завершённую пару DOWN/UP на одном захваченном экземпляре. Навигация выполняется только внутри его decor; даже неотработанная клавиша на краю consumed. Для списка rotary использует DPAD, для ряда кнопок — стандартный последовательный фокус. При закрытии на DOWN UP не переадресуется другому окну. Это не чтение окон стороннего приложения.

Back остаётся в единственной сервисной `DesktopBackSequence`: private protocol16 `injectModalBack(parentDisplayId)` проверяет текущий parent и отправляет одну пару на parent без запроса IME дочернего приложения. UP использует прежний закреплённый токен; второй обычный Back сохраняет возврат Home. Новый публичный SDK для компонентов не вводится. Старую приватную службу startup gate отклоняет до вызова нового метода с просьбой повторной активации.

Runtime regression `wireless-dashboard` проверяет настоящий внешний Binder → диалог, rotary/DPAD → Cancel → OK, отсутствие изменения панели, повторное открытие, игнорирование старого ID и закрытие service Back. `hardware-input` проверяет modal Back → обычный Back → Home на реальном parent. На API34 и API36 обе новые проверки прошли на main/test build29 с первого запуска. API33 прошёл проверку общей Back-последовательности и rotary/OK, но остановился до отправки modal Back на условии `hasWindowFocus`: глобальный фокус не является готовностью input window на отдельном parent. QA30 попытался идентифицировать InputDispatcher window по изменённому после show заголовку; live dumpsys на API37 подтвердил, что input channel сохраняет первоначальное имя Activity. Это вторая ошибка условия готовности стенда, до отправки Back. QA31 вместо глобального фокуса/имени ждёт OnDraw точного собственного decor и завершение его traversal, проверяет parent ID, isShown и layout, затем отправляет ровно одно Back и требует реального закрытия. Состояние InputDispatcher сохраняется лишь для диагностики. Основной build29 этим не меняется; результат остальных модальных проверок дополняется после исполнения. PopupMenu закрепления не расширяется этим путём и остаётся отдельным меню, открываемым касанием.
