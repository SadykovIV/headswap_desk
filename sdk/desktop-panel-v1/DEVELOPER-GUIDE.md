# Как разработать и выпустить профиль для HeadSwap Desktop

Профиль — отдельное Android-приложение со своим именем, интерфейсом, настройками и подписью. После установки оно появляется в списке **«Профиль» на главном экране HeadSwap**. Пользователь выбирает его точно так же, как встроенные режимы. Исходники HeadSwap, изменение его APK, ключ команды HeadSwap и регистрация у разработчика хоста для этого не требуются.

Это руководство для **HeadSwap Desktop 0.5.1, Profile API v1, Android 13+**. Профили v1 также работают с предварительной версией 0.5.0. Номер API, версия HeadSwap и версия APK вашего профиля меняются независимо. Все внешние профили v1 используют движок Android Desktop; они не заменяют DriveDeck или Samsung DeX.

## 1. От пустой папки до установленного профиля

Скачайте [комплект Profile SDK v1](https://github.com/SadykovIV/headswap_desk/releases/download/v0.5.1/HeadSwap-Profile-SDK-v1-dev.zip) и [HeadSwap Desktop 0.5.1](https://github.com/SadykovIV/headswap_desk/releases/download/v0.5.1/HeadSwap-Desktop-0.5.1.apk). На компьютере нужны JDK 17, Android SDK Platform 37 и Platform Tools (`adb`); удобнее всего установить их через Android Studio. Укажите пути к JDK в `JAVA_HOME` и Android SDK в `ANDROID_HOME`. Gradle Wrapper входит в комплект. Первая сборка загружает Gradle и Android Gradle Plugin. На телефоне нужен Android 13 (API 33) или новее.

**Самый короткий путь:** распакуйте ZIP в каталог `headswap-sdk`, перейдите в него и выполните команды ниже. Python 3.8+ нужен только для создания проекта; готовый пример собирается без Python. Подставьте свои уникальные пакет, идентификатор и видимое имя. Название `CarBridge` и ID `carbridge` оставьте соответствующему автору.

```sh
python3 tools/new_profile.py ../RouteBoard --package org.example.routeboard --mode routeboard --name "Мой рабочий стол"
cd ../RouteBoard
./gradlew :app:assembleDebug
adb devices -l
adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk
```

В Windows из PowerShell используйте `py -3` вместо `python3` и `.\gradlew.bat :app:assembleDebug`. Вместо `SERIAL` укажите устройство из `adb devices -l`. Установите на тот же телефон APK HeadSwap, если его ещё нет. Первая установка доступна и обычным системным установщиком из APK. Скрипт создаёт **новый каталог**, сохраняет ваш проект отдельно от SDK и оставляет внутри один вариант приложения (`debug`/`release` — типы сборки). Он не записывает ключ подписи и не меняет файлы другого проекта.

На телефоне остановите подключение и ожидание ГУ; в HeadSwap откройте **«Профиль» → «Мой рабочий стол»**. Сверьте имя пакета и отпечаток сертификата со своим APK, нажмите **«Использовать»**. При необходимости отметьте доступ к сведениям о плеере. Активируйте HeadSwap обычным способом и подключите автомобиль или CarLife HeadUnit Emulator. Ожидаемый результат: на экране ГУ появятся домашняя страница и нижние кнопки **вашего** APK. Откройте каталог и выберите одно из установленных приложений: его окно должно принимать касания, а док оставаться доступным. Отключите и заново подключите ГУ — профиль должен начать новую сессию.

**Если нужен только образец:** из корня распакованного ZIP выполните `./gradlew :app:assembleStarterDebug`. Результат: `app/build/outputs/apk/starter/debug/app-starter-debug.apk`, имя в списке — **«Стартовый рабочий стол»**. В том же комплекте `:app:assembleExampleDebug` собирает минимальную панель, `:app:assembleCarbridgePreviewDebug` — музыкальный пример HeadSwap (историческое имя сборки). Это три отдельных примера. Android Studio может открыть корень ZIP или созданный `RouteBoard` как обычный Gradle-проект.

## 2. Кто отвечает за экран

| Вы делаете в своём APK | HeadSwap делает в хосте |
| --- | --- |
| Домашний экран, каталог, иконки, избранное, виджеты, анимации, темы и настройки | Создаёт дисплей ГУ и управляет его жизненным циклом, видео, вводом, USB/CarLife и приборкой |
| Выбираете публичное приложение, которое хочет открыть пользователь | Проверяет запрос и размещает реальное приложение в отдельном дочернем окне |
| Рисуете собственный док и передаёте размеры рабочей области | Резервирует место под док, меняет размер окна приложения, сохраняет задачу при показе домашней страницы |
| Показываете обложку, заголовок и кнопки плеера по согласию пользователя | Читает текущую доступную медиасессию и отправляет ей поддерживаемые команды |

Небольшая панель может воспользоваться штатной навигацией HeadSwap. Полноэкранный профиль рисует собственные кнопки и каталог. Он остаётся обычной Activity своего APK: нельзя запросить адрес дисплея, внедрить код в хост или получить доступ к микрофону, USB, сырому вводу либо всем уведомлениям через этот SDK.

## 3. Подключение к существующему лаунчеру

Если лаунчер уже существует, выделите его экран в отдельную изменяемую Activity или Android flavor. Используйте отдельный `applicationId`, если исходное приложение и профиль должны устанавливаться рядом. Перенесите представления и свою модель данных в Activity профиля, а действия «открыть приложение», «назад» и изменение компоновки направьте в публичный SDK. Обработчик USB, системный overlay или собственная служба проекции не нужны. Самостоятельную телефонную Activity можно сохранить отдельно.

1. Скопируйте `libs/headswap-desktop-profile-sdk-v1-dev.aar` из ZIP в **`app/libs/`** своего проекта. В зависимостях `app/build.gradle.kts` добавьте `implementation(files("libs/headswap-desktop-profile-sdk-v1-dev.aar"))`. В исходниках ZIP уже есть AIDL для чтения; повторно компилировать этот же интерфейс в приложении рядом с AAR не нужно. Готовая библиотека не добавляет разрешений, Activity или служб.
2. Сохраните постоянными `applicationId`, класс точки входа и `MODE_ID`. `MODE_ID` начинается со строчной латинской буквы или цифры и соответствует `[a-z0-9][a-z0-9._-]{0,63}`. Видимое название может быть локализовано и изменено. Для обычного профиля строка в списке берётся из метки Activity; имя приложения и `android:description` полезны в «Компонентах».
3. Включите вход профиля в манифест. Пример ниже — для полного экрана с собственным доком. Для маленькой панели опустите `PROFILE_CHROME`; для панели без музыки и отдельной компоновки можно опустить и `DASHBOARD`, и `PROFILE_CHROME`.

```xml
<activity android:name=".PanelActivity" android:label="@string/app_name"
    android:exported="true" android:resizeableActivity="true" android:launchMode="standard">
    <intent-filter>
        <action android:name="com.headswap.desk.action.DESKTOP_COMPONENT" />
        <category android:name="android.intent.category.DEFAULT" />
    </intent-filter>
    <meta-data android:name="com.headswap.desk.component.API_MAJOR" android:value="1" />
    <meta-data android:name="com.headswap.desk.component.PROFILE" android:value="android-desktop" />
    <meta-data android:name="com.headswap.desk.component.MODE_ID" android:value="routeboard" />
    <meta-data android:name="com.headswap.desk.component.DASHBOARD" android:value="true" />
    <meta-data android:name="com.headswap.desk.component.PROFILE_CHROME" android:value="true" />
</activity>
```

Для входной Activity используйте `standard` или `singleTop`, обычный режим документов и выключенный перенос задач. Не требуйте закрытого разрешения для запуска Activity. Чтобы показать список программ, объявите `MAIN`/`LAUNCHER` в `<queries>`, как в приложенном примере. Получите точные `ComponentName` из результатов `queryIntentActivities`; одного имени пакета недостаточно. `QUERY_ALL_PACKAGES` для такого каталога не нужен. [Видимость приложений Android](https://developer.android.com/training/package-visibility/declaring).

## 4. Сеанс, жизненный цикл и запуск приложений

Получайте `ProfileSession.from(intent)` в `onCreate`. В `onNewIntent` вызовите `setIntent(newIntent)`, замените ссылку и отбросьте асинхронные результаты прежнего сеанса. `null` нормален при самостоятельном запуске Activity или несовместимом хосте: покажите «Откройте профиль через HeadSwap» и оставьте работающими локальные настройки. Не сохраняйте Binder на диск, не передавайте его службам или другому APK. При `onStop` остановите таймеры и опрос плеера, в `onDestroy` освободите ресурсы. Сохраняйте собственное избранное и идентификаторы приложений, а не дескрипторы окон.

Вызовы сессии выполняйте на рабочем потоке, UI обновляйте на главном. `true` у команд означает, что хост принял запрос для обработки; приложение ещё может не открыться. При `false` оставьте каталог доступным. Хост проверяет активный профиль, UID, подпись, видимость и допустимость запуска; после разрыва USB старый клиент больше не действителен. Для автоматического восстановления сначала дождитесь `onResume` и принятого `setDashboardLayout`, затем отправьте один запрос. Отменяйте отложенное восстановление при ручном выборе, Home и уходе с экрана. Не крутите цикл до получения `true`.

| Вызов `ProfileSession` | Что проверяет и что возвращает |
| --- | --- |
| `getApiMajor()`, `supports(bit)` | Версию и одну известную возможность за вызов. Для объединения нескольких битов используйте отдельные проверки. |
| `canLaunchApps()` / `requestLaunch(component)` | Открывает выбранную экспортируемую `MAIN/LAUNCHER` Activity без специального разрешения. Обычный профиль поддерживает `standard` и `singleTop`. Для полноэкранного профиля допустим `singleTask`; если уже запущенное приложение надо перенести с телефона, это подтверждает пользователь на ГУ. |
| `canOpenCatalog()` / `openCatalog()` | Запрашивает каталог HeadSwap. Для собственной сетки рисуйте её в своей Activity. |
| `canUseProfileChrome()` / `setDashboardLayout(musicVisible, musicOnRight, targetVisible, dockHeightPx)` | Управляет областью карты относительно интерфейса профиля. `targetVisible=false` раскрывает свою Activity, сохраняя задачу приложения. |
| `sendDashboardAction(action)` | `DASH_BACK` запрашивает «Назад» для целевого окна; `DASH_NAVIGATION` возвращает область приложений к навигации хоста; `DASH_PHONE_TOGGLE` запрашивает действие с экраном телефона по его настройкам и с подтверждением. |
| `canUseMedia()` / `getNowPlaying()` | Метаданные видимой музыкальной карточки или `null`. Доступ не гарантирует, что сейчас играет музыка. |
| `sendMediaCommand(command)` | `MEDIA_PREVIOUS`, `MEDIA_PLAY_PAUSE`, `MEDIA_NEXT`. `false` означает, что команда не отправлена. |

## 5. Компоновка, DPI и касания

Считайте размер из `resources.displayMetrics` **Activity профиля на ГУ** и измеряйте её контейнер после layout. Не берите метрики физического экрана телефона и не меняйте его `wm density`. Экран профиля принадлежит вашему APK; окно запущенной программы выводится поверх лишь в отведённом прямоугольнике. При `musicVisible=true` хост отводит карточке 30% ширины выбранной стороны; `false` возвращает ширину приложению. Высота дока задаётся в пикселях дисплея ГУ: например `round(46 * resources.displayMetrics.density)` для 46 dp. В этой версии хост ограничивает резерв величиной до 96 dp и до одной пятой высоты экрана, даже если профиль запросил больше.

Используйте один рассчитанный размер одновременно для своей панели и `setDashboardLayout`. При открытии каталога переключайте `targetVisible`, не перезапуская карту. При смене размеров применяйте новую компоновку, а не масштабируйте готовый экран. Для дока оставляйте удобную область нажатия, рисунок внутри центрируйте и масштабируйте одинаково по обеим осям. Часы и заряд измеряйте по тексту; оставшееся место отдайте индикаторам. Проверьте широкий ГУ и 4:3. [Работа Android Activity в изменяемых окнах](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode).

## 6. Музыка, голос и приборка

Для музыкальной карточки пользователь отдельно отмечает разрешение в выборе профиля. Сам HeadSwap должен иметь доступ к активной медиасессии. При `canUseMedia()` читайте `getNowPlaying()` с умеренной частотой только пока панель видна. Показывайте заголовок, исполнителя, состояние и необязательную обложку (до 192 × 192 px); при `null` очистите сведения. Отправляйте команды по нажатию пользователя. Не сохраняйте историю прослушивания без отдельной функции, о которой пользователь знает.

Микрофон и голосовой канал зарезервированы независимо: в API v1 `canUseMicrophone()` и `canUseVoiceChannel()` возвращают `false`, методов для записи и обмена аудио нет. Профиль не подписывается через SDK на сырые уведомления, не подменяет канал HUD и не перехватывает системные клавиши. Навигационное приложение можно показывать живым в дочернем окне. Приборка и HUD автомобиля обслуживаются HeadSwap отдельно от UI профиля.

## 7. Обновление, подпись и удаление

Первый APK пользователь устанавливает обычным способом. После установки в **«Настройки» → «Компоненты HeadSwap Desktop»** появляется карточка с именем установленного компонента, версией и пакетом. Если один APK предоставляет несколько профилей, карточка одна на пакет: установка и удаление Android относятся ко всему APK.

Создайте **собственный постоянный ключ** для распространения Android APK. Для пробной локальной установки достаточно debug-подписи. Для публичного выпуска в Android Studio выберите **Generate Signed Bundle / APK → APK**, свой keystore и конфигурацию release. Храните закрытый ключ отдельно от репозитория. Передайте пользователю SHA-256 сертификата по известному ему каналу и SHA-256 файла для проверки загрузки. Это два разных значения. Проверить сертификат готового файла можно командой из Android SDK Build Tools:

```sh
apksigner verify --verbose --print-certs profile-release.apk
```

Для обновления сохраните пакет, класс, ID режима и сертификат и увеличьте **`versionCode`**. Одного изменения `versionName` недостаточно. Опубликуйте подписанный APK и версию. Если хотите показать ссылку в карточке, разместите на Activity `com.headswap.desk.component.UPDATE_PAGE` со значением HTTPS-страницы **именно этого APK**. Ссылка необязательна: она ведёт на страницу автора. Она не является каталогом автообновлений и не запускает фоновую установку.

Пользователь останавливает проекцию выбранного компонента, нажимает **«Обновить из APK…»**, выбирает файл и подтверждает установку в Android. HeadSwap сверяет пакет, набор текущих подписантов и больший код версии; при несовпадении система установки не открывается. Для удаления кнопка **«Удалить компонент…»** вызывает отдельный системный диалог. Отмена оставляет приложение на месте; удаление всего APK убирает его профили из списка. Если потерян ключ, у пользователя нет обычного пути обновить установленный экземпляр из этой карточки под другой подписью. [Подпись выпусков Android](https://developer.android.com/studio/publish/app-signing).

## 8. Если что-то пошло не так

| Симптом | Что проверить первым |
| --- | --- |
| Профиля нет в списке | Совместимый HeadSwap, тот же Android-пользователь, установленный и включённый пакет; фильтр `DEFAULT`, метаданные на Activity, целочисленный major `1`, регистр ID. Проверьте **merged manifest** собранного APK. |
| `ProfileSession.from()` вернул `null` | Activity открыта напрямую или с устаревшим intent. Откройте из «Профиль» в HeadSwap и после переподключения возьмите новый клиент. |
| После выбора видна пустая область | Дождитесь размеров контейнера и принятой компоновки. Покажите собственную сетку, пока нет цели. Проверьте точный launcher component; для тёплого `singleTask` посмотрите диалог на ГУ. |
| Нет трека или кнопка не сработала | Проверьте отдельное согласие профилю, доступ HeadSwap к медиасессиям, видимость музыкальной панели, наличие активного плеера и поддержку конкретной команды. |
| Касание попадает не туда или карта перекрывает док | Сопоставьте реальные размеры Activity, её `density`, `dockHeightPx`, сторону музыкальной панели и `targetVisible`. Не рассчитывайте координаты по телефону. |
| «Обновить из APK…» отказывает | Остановите активную проекцию, сверьте `applicationId`, текущий сертификат и новый `versionCode`; если Android запросил разрешение источнику HeadSwap, решение принимает пользователь. |

Перед передачей другим проверьте холодное и повторное подключение, выбор из нескольких профилей, состояние при отказе SDK, Home/Back и касания в живом окне, две геометрии и DPI, отсутствие плеера, отказ в доступе к музыке, обновление под прежним ключом и отмену/подтверждение удаления. Убедитесь, что обычный Android Desktop после смены профиля возвращает штатный интерфейс и масштаб экрана телефона не изменился.

## 9. Что входит в комплект и как пересобрать SDK

`libs/` содержит готовый AAR; `sdk-source/` — соответствующие исходники Android-библиотеки и тесты; `api/` — AIDL для просмотра; `app/src/` — три исходных примера для APK; `tools/new_profile.py` создаёт автономный проект с вашей идентичностью. `SHA256SUMS.txt` перечисляет содержимое ZIP, кроме самого файла сумм. На macOS/Linux проверить его можно через `shasum -a 256 -c SHA256SUMS.txt`. Условия распространения исходников HeadSwap/SDK и примеров — в приложенном `LICENSE` (GPLv3). APK CarBridge и ресурсы других авторов в SDK не входят.

Чтобы пересобрать сам AAR и прогнать его тесты из ZIP, выполните `./gradlew -p sdk-source assembleRelease testDebugUnitTest` (Windows: `.\gradlew.bat -p sdk-source assembleRelease testDebugUnitTest`). Собранная библиотека будет в `sdk-source/build/outputs/aar/`. При изменении своей панели пересобирайте свой APK: хост пересобирать не нужно.

### Notification entry (optional capability 64)

A visible panel can call `getNotificationStatus(true)` about once per second. The returned Bundle contains `enabled`, `connected`, and `count`; it never contains notification text or PendingIntents. Hide the panel's native entry when `enabled` is false. Call `getNotificationStatus(false)` when the entry is hidden or the Activity pauses. While a native entry refreshes its visibility, HeadSwap hides its duplicate floating handle; a stale visibility lease expires automatically.

Call `openNotifications()` only after a click on that entry. HeadSwap displays its own notification shade on the current HU display. Card actions remain entirely in HeadSwap: only current same-user Activity PendingIntents are accepted, and the target receives a managed fullscreen window with Back/Home controls. Unknown/older hosts return no notification capability, so components must retain their previous UI without attempting the new IPC methods. Installing this SDK does not itself add a notification button to a third-party component; its author wires the native control.
