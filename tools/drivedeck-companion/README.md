# DriveDeck 0.6.8 для HeadSwap Desktop (code301)

Скрипты собирают отдельное приложение для HeadSwap Desktop из оригинального APK 0.6.8 code300. Исходный APK доступен в [стабильном релизе автора](https://github.com/RotkivKiv/DriveDeck-Updates/releases/tag/stable-code300). Результаты сборки сохраняются в отдельном каталоге.

Code301 устанавливается поверх прежнего компонента code263 с сохранением данных и подключается к службе HeadSwap в пакете `com.headswap.desk`. Обновление доступно в разделе «Компоненты» HeadSwap или через ручную установку адаптированного APK.

Адаптированный пакет — `ru.drivedeck.headswap`, Activity — `ru.drivedeck.launcher.MainActivity`. У него отдельные данные. Для обновления существующей копии нужна прежняя подпись; для связи с HeadSwap оба APK должны быть подписаны **одним ключом**.

В code260 отключены только штатные проверки и загрузки обновлений самого DriveDeck: автоматический таймер, ручная проверка, загрузка APK и выбор штатных каналов. В настройках сохранены пресеты, сведения устройства и диагностика; вместо блока обновлений показана инструкция устанавливать адаптированный APK только из комплекта HeadSwap. Общие HTTP/download-методы модулей и ветка обновления погоды сохранены. В code301 отключены также унаследованные из 0.6.8 функции запуска точки доступа телефона и подключения к аппаратному Bluetooth-контроллеру магнитолы.

## Что делает адаптация

- Главный экран совмещает встроенную карту справа и музыкальный виджет, часы и погоду слева. Отдельная страница показывает два настоящих приложения, например навигатор и плеер.
- `TextureView` получает изображение дочернего дисплея, созданного активной службой HeadSwap. Companion не получает shell Binder и не запрашивает собственное разрешение Shizuku. Доступ к ограниченному gateway защищён подписью и проверкой UID; максимум — два дочерних дисплея текущей сессии DriveDeck.
- Касания и Back направляются в нужную область. Surface сохраняется до подтверждения закрытия producer либо смерти его отдельного пустого lifetime Binder; опрос состояния приложения выполняется вне UI-потока. После смены страницы прежние области закрываются.
- Сохраняются выбранные приложения и пользовательские макеты. Только точное совпадение со старым стандартным макетом 0.6.7 или адаптации 0.2.0 заменяется новым. Если выбор пуст, настройка использует ранее сохранённые пакеты, затем установленные Яндекс Навигатор/Яндекс Музыку. Обхода всех приложений для случайного выбора нет.
- Удалены HOME/LAUNCHER/ASSIST-регистрация, запрос роли HOME, системный UID, root-команды, автозапуск, телеметрия и изменение общей темы/яркости. Нет overlay-разрешения или `Presentation`. Собственные полноэкранные запуски также остаются на дополнительном дисплее.

Для встроенных приложений нужен активный доступ HeadSwap и поддержка дополнительных дисплеев на телефоне. В HeadSwap 0.2.10 можно активировать доступ с телефона или компьютера; отдельно доступен вариант Shizuku. Доступ необходимо активировать снова после перезагрузки. Это не отдельная Android-система: приложения используют обычные данные и аккаунты, а существующая задача может переместиться с телефона. Защищённые поверхности, несовместимые приложения и особенности прошивки могут ограничивать отображение. Канал звука настраивается отдельно в HeadSwap.

Начиная с code261 вид карты **Яндекс Навигатора** (`ru.yandex.yandexnavi`) привязан к DPI родительского экрана HeadSwap. Базовый вид при 160 DPI сохранён: область 1022×876 с масштабом области 85% рисуется в 2044×1752 при 272 DPI. При 200 DPI элементы карты должны быть в 1,25 раза крупнее базовых, при 128 DPI — в 0,8 раза. Для этого коэффициент внутреннего буфера равен `320 / DPI родительского экрана`, а DPI дочернего окна меняется тем же коэффициентом. Обычные элементы Android при этом следуют выбранному размеру интерфейса. Если требуемое сглаживание выходит за допустимые 3840×2160, используется ближайший доступный коэффициент; при низком DPI результат может отличаться от идеальной пропорции. Общий лимит памяти двух окон не повышается.

При возврате в DriveDeck видимая карта повторно применяет размер буфера и ждёт подтверждения дочернего дисплея; уже открытый на нём Навигатор не перезапускается. Отложенное восстановление отменяется при следующем уходе с рабочего стола. Если прежний экран ещё закрывается, тот же буфер повторно используется только после подтверждённого освобождения прежнего производителя; ожидание не запускает дополнительных экранов. Музыка, Яндекс Карты и другие пакеты не получают профиль Навигатора. У прежнего gateway без capability bit 0 остаётся обычное разрешение; расширенные размеры требуют bit 3. Проверки именно текущего APK указаны в `BUILD_REPORT.json` выпуска; результат сборки не заменяет проверку на телефоне.

Касания проходят существующее преобразование `render pixels / TextureView pixels` ровно один раз. Изменение буфера и параметров renderer выполняется на UI-потоке, создание/resize — в последовательной очереди Binder. Во время неподтверждённого resize ввод блокируется; потерянный ответ не считается подтверждением старого размера. В адаптации 0.2.8 при capability bit 3 максимум одного буфера — 3840×2160, DPI 1280; HeadSwap ограничивает общий бюджет дочерних дисплеев. Повышенное разрешение увеличивает нагрузку на GPU и память. Изменения не затрагивают APK Навигатора, его настройки или параметры экрана телефона.

Для 0.2.5 добавлены ограниченные повторы resize: запросы объединяются до последней геометрии, после ошибки выполняются не более трёх повторов через 250, 1000 и 3000 мс. Неизменный layout не сбрасывает этот лимит; новый размер заменяет ожидающий запрос. Запуск приложения ждёт подтверждённого размера, ввод до ACK блокируется. Отправка release повторяется через 500, 1500 и 5000 мс только прежнему gateway и прежнему handle.

Опциональные capabilities расширяют прежний протокол 1: bit 1 — два указателя (`touchPoints`, transaction 9), bit 2 — пустой Binder срока жизни процесса producer (`producerLifetime`, transaction 10). Pointer IDs, action index и координаты копируются из уже преобразованного `MotionEvent`; повторного масштабирования нет. Без bit 1 сохраняется прежний одиночный ввод. Отдельный lifetime Binder не даёт методов, команд или привилегий. После его смерти consumer можно освободить; после обычного release ACK death listener снимается. Смерть общего gateway, тайм-аут или неизвестный результат create не считаются ACK. Если create не вернул handle и lifetime token получить не удалось, потенциально используемый Surface по-прежнему удерживается до безопасного завершения процесса.

Минимальная версия Android определяется конкретной сборкой HeadSwap; успешная компиляция не подтверждает совместимость со всеми прошивками. Изменения 0.2.5 проверены локальными тестами состояния и компиляцией Java/AIDL; проверка нового APK на телефоне записывается отдельно.

На проверяемом Samsung подтверждены изображение карты на основном экране и одновременное отображение навигатора с музыкой на странице двух приложений, с закрытием прежнего дочернего дисплея. Проверки ввода и полного жизненного цикла записываются отдельно в `BUILD_REPORT.json` соответствующей сборки. Эта отметка не подтверждает все функции или другие устройства.

## Пересборка

Нужны Python 3, JDK 17, Android SDK с `platforms/android-37.0` и `build-tools/36.0.0`, стандартный debug keystore с той же подписью, что у HeadSwap, и [Apktool 3.0.3](https://github.com/iBotPeaches/Apktool/releases/tag/v3.0.3). Положите зависимости вне этого каталога. `--work` — отдельная папка результатов; повторная сборка пересоздаёт её `decoded`, `generated-aidl` и каталоги helper-компиляции.

```sh
python3 tools/drivedeck-companion/build.py \
  --original "/path/DriveDeck-0.6.8-code300.apk" \
  --work "/path/companion-build-output" \
  --jdk "/path/jdk17" \
  --sdk "/path/android-sdk" \
  --apktool "/path/apktool_3.0.3.jar" \
  --keystore "/path/headswap-debug.keystore"
```

Поддерживается стандартный debug keystore: alias `androiddebugkey`, стандартный debug-пароль `android`. Ключ не создаётся и не скачивается. Для другой схемы подписи измените signing-команду в своей копии скрипта; пароли и ключи не добавляйте в исходники.

Скрипт проверяет хеш оригинального APK и Apktool, декодирует оригинал, применяет `patch.py`, генерирует Java из AIDL, проверяет изоляцию штатного обновления приложения, политику геометрии, очередь повторов, условия освобождения Surface и пакеты касаний, затем компилирует helper-классы, добавляет их DEX, собирает и подписывает APK. Затем проверяет подпись, zipalign и ограничения manifest. Результаты: `DriveDeck-HeadSwap-0.6.8-code301.apk` и `patch-report.json` внутри `--work`. Статус `build: PASS` не означает успешную проверку на телефоне. Бинарная идентичность APK при другой среде или подписи не гарантируется.

## Состав и лицензирование

`patch.py` адресован только точной исходной версии APK и проверяет ожидаемые smali-фрагменты. `DisplayOnlyLaunch.java` ограничивает полноэкранные запуски текущим дополнительным дисплеем и переносит стандартный макет. `EmbeddedDisplayClient.java` управляет Surface, Binder-связью, вводом и выбором первоначальных приложений. `EmbeddedRenderProfile.java` задаёт ограниченную геометрию конкретного пакета; `EmbeddedResumeGate.java`, `EmbeddedRetryGate.java`, `EmbeddedSurfaceRelease.java` и `EmbeddedTouchPacket.java` содержат проверяемые правила возврата, повторов, ACK и копирования ввода; standalone-тесты находятся в `tests/`. `build.py` в этом каталоге отличается от временного скрипта переносимыми обязательными путями; логика адаптации сохранена.
